Curso Android: SimpleTaskManagement

Bienvenido: cómo usar este curso

Este curso te enseña a reconstruir desde cero una aplicación real: un gestor de tareas llamado SimpleTaskManagement, que guarda todo en una base de datos local y se sincroniza con Google Tasks. Está escrito para alguien que ya programa en Python, así que nunca se explica qué es una variable, un bucle o una función. Solo se explica lo que cambia en Kotlin y en Android.

Cada módulo tiene texto pensado para ser escuchado con un lector de voz, y debajo bloques de código colapsables. Puedes escuchar la explicación completa sin que el lector recite código. Abre el bloque solo cuando quieras verlo. El botón Escuchar lee únicamente la prosa del módulo.

La app sigue Clean Architecture con MVVM. Hay tres capas: dominio, con modelos, casos de uso y la interfaz del repositorio; datos, con Room, Retrofit, autenticación y sincronización; y presentación, con pantallas Compose y ViewModels. La inyección de dependencias la hace Hilt, la asincronía las corrutinas y Flow, y el trabajo en segundo plano WorkManager.

Todos los fragmentos de código provienen del código real del repositorio, recortados para enseñar. Al final hay un módulo de hallazgos con errores y deuda técnica que encontré en la app, entre ellos un fallo crítico en la cabecera de autorización.

Módulo 1. Entorno, Gradle y manifiesto

Instala Android Studio y crea un proyecto con la plantilla Empty Activity de Compose. Usa nombre de paquete com.example.simpletaskmanagement. El proyecto usa Android Gradle Plugin 9.2.1, Kotlin 2.2.10, minSdk 24, y compileSdk y targetSdk 36, con Java 17.

Las versiones no se escriben en el build. Viven en gradle/libs.versions.toml, el catálogo de versiones. Es el equivalente a un requirements.txt con alias tipados: en el build escribes libs.hilt.android en lugar de una cadena con versión. Así actualizas una librería en un solo sitio.

Además de los plugins habituales, el proyecto usa el plugin de compilador de Compose, KSP y el plugin de Hilt. KSP, Kotlin Symbol Processing, es el procesador de anotaciones moderno que genera código para Room y Hilt. Sustituye a kapt y es bastante más rápido.

La plataforma de Compose se importa con el BOM, Bill of Materials: una sola versión que alinea todas las librerías de Compose. Por eso esas dependencias se declaran sin número de versión.

En el manifiesto hay tres permisos: INTERNET, ACCESS_NETWORK_STATE y RECORD_AUDIO. Se declara una clase Application propia, TaskApplication, y una sola actividad con windowSoftInputMode adjustResize para que el teclado no tape los formularios. Un detalle importante: se elimina el inicializador automático de WorkManager, porque lo inicializa Hilt bajo demanda.

Módulo 2. Kotlin Core para Pythonistas

Kotlin es de tipado estático, con inferencia, así que escribes pocos tipos. La mayor diferencia respecto a Python es la nulabilidad: un tipo normal nunca puede ser nulo. Para permitirlo añades un signo de interrogación. El compilador te obliga a manejar el caso nulo con el operador de llamada segura, el operador elvis, o una comprobación explícita. Es como tener Optional verificado por mypy en modo estricto, pero obligatorio.

Se distingue val, inmutable, de var, mutable. Por idioma, usa val siempre salvo necesidad. Las data class equivalen a dataclass con frozen: generan igualdad, toString, desestructuración y el método copy, que crea una instancia modificada. Todo el estado de la app se actualiza con copy, nunca mutando.

Las enum class y las sealed class permiten modelar estados cerrados. La expresión when es exhaustiva sobre ellas: si olvidas un caso, no compila. Es el match de Python pero verificado. En el proyecto, SyncState es un enum y el resultado de autorización es una sealed interface.

Las funciones de extensión añaden métodos a tipos existentes sin heredar. El TaskMapper define toDomain, toEntity y toDto como extensiones, y se leen como si fueran métodos propios de la entidad.

Los parámetros con valor por defecto y los argumentos con nombre sustituyen a los kwargs. Las lambdas se escriben entre llaves; si la última es un parámetro, va fuera del paréntesis, y si hay un solo parámetro se llama it. Las funciones de ámbito let, apply, also y run permiten encadenar configuración. Los valores se interpolan en cadenas con el signo de dólar.

Un object es un singleton declarado en el lenguaje. Un companion object es el equivalente a los miembros estáticos. Y la convención de operator fun invoke permite llamar a una instancia como una función: así se escriben todos los casos de uso, y se usan como saveTask de la tarea.

En colecciones, tienes map, filter, groupBy, associate, filterValues y similares, evaluados de forma inmediata sobre listas, equivalentes a las comprensiones. Para evaluación perezosa existe asSequence. También encontrarás by lazy para propiedades de inicialización diferida, require para validar argumentos lanzando IllegalArgumentException, y la anotación OptIn para APIs experimentales de Material3.

Módulo 3. Jetpack Compose: interfaz declarativa

Compose describe la interfaz como funciones. Una función anotada con Composable emite elementos de interfaz; no devuelve vistas. Cuando cambia el estado que lee, Compose vuelve a ejecutarla: a eso se le llama recomposición. Piensa en un render de React, pero con el compilador rastreando qué estado lee cada función.

El estado se guarda con remember y mutableStateOf. Remember conserva el valor entre recomposiciones, pero no sobrevive a un cambio de configuración como rotar la pantalla; para eso existe rememberSaveable o, mejor, un ViewModel. Se usa la sintaxis by para delegar y leer el valor sin escribir punto value.

La regla de oro es el elevado de estado, state hoisting. Un composable de bajo nivel recibe el valor y una lambda de evento, y no guarda estado propio. Flujo de datos hacia abajo, eventos hacia arriba. TaskItem, SearchBarComponent o AddCategoryDialog siguen este patrón y por eso son fáciles de probar y previsualizar.

El Modifier es una cadena inmutable de decoraciones: tamaño, relleno, clic, fondo. El orden importa; por ejemplo padding antes o después de background produce resultados distintos. Por convención todo composable público acepta un modifier como primer parámetro opcional.

La pantalla principal usa Scaffold de Material3, que ofrece huecos para barra superior, barra inferior, botón flotante y host de Snackbar. En la barra inferior se coloca el banner de anuncios. Para listas se usa LazyColumn, que solo compone lo visible. Con stickyHeader las cabeceras de grupo como Hoy o Mañana se quedan fijas, y el parámetro key en items da identidad estable a cada fila para animaciones y para conservar estado al reordenar.

Para efectos secundarios existen LaunchedEffect, que lanza una corrutina cuando cambia su clave, y DisposableEffect para limpiar. La pantalla de edición usa LaunchedEffect con el id de la tarea para cargarla, y otro con la bandera de guardado para navegar hacia atrás. Nunca navegues ni lances corrutinas directamente en el cuerpo del composable.

Para integrar vistas clásicas, como el anuncio de AdMob, se usa AndroidView. Para recibir resultados de otras actividades, rememberLauncherForActivityResult con un contrato: se usa para reconocimiento de voz y para la autorización de Google. Los diálogos como AlertDialog son simplemente composables que se muestran si una bandera es verdadera.

El tema se define con MaterialTheme y un ColorScheme propio claro y oscuro. La función SimpleTaskManagementTheme recibe darkTheme y envuelve la app, de modo que la preferencia de modo oscuro del usuario puede controlar todo el árbol.

Módulo 4. Navegación, Drawer y ViewModels con Hilt

La app tiene una sola actividad, y la navegación entre pantallas la gestiona Navigation Compose. Las rutas son cadenas declaradas en un objeto NavRoutes: lista de tareas, crear tarea, editar tarea con un argumento de id, y ajustes. El NavHost mapea cada ruta a un composable. El argumento se declara con navArgument y se lee del backStackEntry.

Sobre el NavHost se coloca un ModalNavigationDrawer. El menú lateral muestra las categorías con un Badge que indica cuántas tareas tiene cada una, y permite crear nuevas. El estado de abrir y cerrar el cajón se controla con un DrawerState y se manipula desde una corrutina.

Cada pantalla obtiene su ViewModel con hiltViewModel. Hilt crea el ViewModel, inyecta sus dependencias y lo asocia a la entrada del back stack. Por eso la clase lleva la anotación HiltViewModel y un constructor con Inject.

La UI observa el estado con collectAsStateWithLifecycle, que solo recolecta mientras la pantalla está al menos en estado Started. Es la forma correcta de consumir StateFlow en Compose, porque evita trabajo mientras la app está en segundo plano.

La app raíz también aplica el tema oscuro según el ViewModel y registra un lanzador de resultados para el flujo de consentimiento de Google, porque la autorización puede devolver un PendingIntent que debe ejecutarse desde una actividad.

Módulo 5. Corrutinas y Flow

Una función suspend puede pausarse sin bloquear el hilo, como un await de asyncio, pero sin necesidad de marcar al llamante con una palabra distinta: basta con que también sea suspend o esté dentro de una corrutina. Las corrutinas se lanzan en un CoroutineScope con launch, que no devuelve valor, o async, que devuelve un resultado diferido. La concurrencia es estructurada: cancelar el padre cancela a los hijos, al estilo de los TaskGroup de Python.

En un ViewModel se usa viewModelScope, que se cancela cuando el ViewModel muere. Los dispatchers deciden el hilo: Main para la interfaz, IO para disco y red, Default para cálculo. Room y Retrofit ya mueven su trabajo fuera del hilo principal en las funciones suspend, así que rara vez necesitas withContext.

Flow es un flujo asíncrono de valores, como un generador asíncrono. Los DAO de Room devuelven Flow, y cada vez que cambia la tabla se emite una lista nueva. Es lo que hace la interfaz reactiva sin recargar manualmente.

El MainViewModel combina varios flujos con combine: la categoría seleccionada, el texto de búsqueda y las tareas. Cuando cambia la categoría o la búsqueda, flatMapLatest cancela la consulta anterior y empieza otra. Después stateIn convierte el flujo frío en un StateFlow caliente con la política WhileSubscribed de cinco mil milisegundos. Esto significa que el flujo se mantiene vivo cinco segundos tras desaparecer el último suscriptor, lo suficiente para sobrevivir a una rotación sin reiniciar consultas.

Para estado mutable de formularios se usa MutableStateFlow con update y copy: la actualización es atómica y segura entre hilos. Se expone hacia fuera como StateFlow de solo lectura.

Para envolver APIs con callbacks, como las Tasks de Play Services, se usa suspendCancellableCoroutine. Se registra el listener de éxito y de error y se reanuda la corrutina con resume o resumeWithException. Y la cancelación cooperativa es clave: si capturas Exception de forma amplia dentro de una corrutina, relanza CancellationException.

Módulo 6. Ciclo de vida de Android

En Android el sistema es dueño del proceso. Tu Activity puede destruirse y recrearse al rotar, cambiar de tema o tras presión de memoria, y todo el proceso puede ser eliminado en segundo plano. No hay un main que controles; hay callbacks. Los principales estados de una actividad son Created, Started y Resumed, y sus inversos.

La clase Application vive tanto como el proceso. TaskApplication aprovecha eso para inicializar el SDK de anuncios y para proporcionar la configuración de WorkManager con la fábrica de Hilt. Es el lugar para inicializaciones globales, pero debe ser ligero porque retrasa el arranque.

MainActivity es mínima: activa edge-to-edge, para dibujar bajo las barras del sistema, y llama a setContent con AppNavigation. Toda la lógica está fuera de la actividad.

El ViewModel sobrevive a los cambios de configuración, pero no a la muerte del proceso. Para eso existe SavedStateHandle, donde guardas pequeñas claves como el id de la tarea en edición. En esta app el modo oscuro vive solo en memoria, por lo que se pierde si el proceso muere; es una de las deudas listadas al final.

Los efectos de lifecycle en Compose se resuelven con collectAsStateWithLifecycle, que pausa la recolección cuando la pantalla no es visible, y con LaunchedEffect y DisposableEffect para suscribirte y limpiar. Además, el trabajo que debe sobrevivir al cierre de la app no pertenece a un ViewModel sino a WorkManager, que veremos en el módulo de sincronización.

Módulo 7. Clean Architecture, casos de uso e inyección con Hilt

La regla de dependencias dice que las capas externas dependen de las internas, nunca al revés. El dominio no conoce Android, Room ni Retrofit. Define modelos y la interfaz TaskRepository. La capa de datos la implementa. La presentación solo habla con casos de uso. Es el principio de inversión de dependencias con un protocolo de Python como interfaz.

Cada caso de uso es una clase pequeña con una única operación pública, invocada con operator invoke. Reciben el repositorio por constructor. Así la lógica de negocio, como agrupar tareas por fecha o recortar el título, se prueba sin emulador.

Los mappers convierten entre tres representaciones de una tarea: la entidad de Room, el DTO de la API y el modelo de dominio. Mantenerlas separadas permite que un cambio de esquema remoto no rompa la interfaz. Un detalle real: Google Tasks guarda la fecha de vencimiento solo como fecha a medianoche UTC, así que el mapper la traduce a las nueve de la mañana locales del mismo día.

Hilt resuelve el grafo. Los módulos con Module e InstallIn SingletonComponent dicen cómo construir lo que no se puede anotar con Inject: la base de datos, el cliente HTTP y Retrofit. Binds enlaza una interfaz a su implementación, así RepositoryModule vincula TaskRepository con TaskRepositoryImpl. Los ViewModels y Workers usan sus propias anotaciones.

Módulo 8. Persistencia con Room

Room es un ORM sobre SQLite con verificación de SQL en tiempo de compilación. Declaras entidades con Entity, DAOs con Dao y la base de datos con Database. KSP genera la implementación. Lo más parecido en Python sería SQLAlchemy, pero aquí los errores en una consulta rompen la compilación, no la ejecución.

La entidad de tarea usa como clave primaria un UUID en texto llamado localId, generado en el dispositivo, y un remoteId nulo que se rellena cuando Google asigna un id. Tener ambos es la base del enfoque offline-first. Una clave foránea enlaza cada tarea con su categoría con borrado en cascada, y se indexa categoryId.

Cada fila lleva un SyncState: sincronizada, pendiente de crear, de actualizar o de borrar. Los borrados son lógicos, marcando la fila como PENDING_DELETE, para poder avisar al servidor después. Las consultas de interfaz excluyen esas filas.

Los DAO devuelven Flow para lecturas observables y funciones suspend para escrituras. Un TypeConverter guarda el enum SyncState como texto. Para contar tareas por categoría se usa una consulta con JOIN y GROUP BY cuyo resultado se mapea a una clase tuple con Embedded.

La categoría por defecto, Mis tareas con remoteId arroba default, se inserta en un callback onCreate de la base de datos. Como el callback necesita la base de datos ya construida, se inyecta un Provider para obtenerla de forma diferida. Ojo: la app usa fallbackToDestructiveMigration y exportSchema falso, válidos en desarrollo pero peligrosos en producción, porque un cambio de esquema borraría los datos del usuario.

Módulo 9. Redes con Retrofit, OkHttp y Gson

Retrofit convierte una interfaz Kotlin en un cliente HTTP. Cada método lleva anotaciones con el verbo y la ruta, y es suspend, por lo que se usa directamente desde corrutinas. Los parámetros de ruta, de consulta y el cuerpo se anotan con Path, Query y Body. Gson convierte JSON en data classes; con SerializedName mapeas nombres de campo cuando difieren.

La API usada es Google Tasks, con base https colon barra barra tasks punto googleapis punto com. Se consumen las listas de tareas, que la app llama categorías, y las tareas dentro de cada lista. Se usa GET para leer, POST para crear, PATCH para actualizar parcialmente y DELETE para borrar.

OkHttp es el cliente subyacente y admite interceptores, que son middleware. AuthInterceptor añade la cabecera Authorization con el token de acceso, y si la respuesta es 401 pide un token nuevo y reintenta una vez. El orden importa: el interceptor de logging se registra después para ver la petición ya modificada.

Atención: el código actual tiene un error crítico en este interceptor. La cabecera se establece con una cadena literal de asteriscos en lugar de la palabra Bearer seguida del token, por lo que ninguna petición autenticaría. Corrígelo como se muestra abajo. Además, el logging en nivel BODY imprime cabeceras y cuerpos sensibles, y debe limitarse a compilaciones de depuración.

Módulo 10. Autenticación con Google

Para llamar a Google Tasks necesitas un token OAuth con el alcance de tasks. La app usa el cliente de autorización de Google Identity, AuthorizationClient, en lugar de la API antigua de Sign-In. Pides el alcance, y el resultado puede ser un token directo si el usuario ya consintió, o un PendingIntent que debes lanzar para mostrar la pantalla de consentimiento.

El PendingIntent se ejecuta con un launcher de StartIntentSenderForResult registrado en la raíz de Compose. Al volver, se extrae el resultado con getAuthorizationResultFromIntent, y se guarda el token. Es un patrón típico de Android: operaciones que necesitan UI del sistema se devuelven como intents para que la actividad los lance.

La clase AuthManager guarda el token y expone un StateFlow booleano, authState, que indica si hay sesión. La interfaz se suscribe y cambia entre Iniciar sesión y Cerrar sesión. Hoy usa SharedPreferences normales; para producción debería usar almacenamiento cifrado.

Para configurarlo en Google Cloud Console debes crear un cliente OAuth de tipo Android con el nombre de paquete y la huella SHA-1 de tu clave de firma, habilitar la API de Google Tasks y configurar la pantalla de consentimiento. Sin la SHA-1 correcta, la autorización fallará en silencio.

Módulo 11. Sincronización offline-first con WorkManager

Offline-first significa que la base de datos local es la fuente de verdad. La interfaz nunca espera a la red. Cuando el usuario crea, edita o borra, el repositorio escribe en Room con un estado pendiente y luego programa una sincronización. Si no hay conexión, WorkManager espera y la ejecuta cuando vuelve, incluso si la app se cerró.

La sincronización tiene dos fases. Primero el push: se envían las categorías pendientes y luego las tareas pendientes, creando, actualizando o borrando según su estado. Después el pull: se descargan las listas y tareas remotas, y se insertan o actualizan localmente. La resolución de conflictos es last-write-wins: se compara la fecha de actualización, y solo se sobrescriben filas ya sincronizadas, para no pisar cambios locales pendientes.

Un caso particular: si una tarea nunca llegó al servidor y el usuario la borra, se elimina físicamente de inmediato, porque no hay nada que borrar en remoto.

SyncManager encola un trabajo único de una sola ejecución con política REPLACE y restricción de red conectada. También define una sincronización periódica cada quince minutos con política KEEP, pero ese método nunca se invoca en el código actual, y es trabajo pendiente: debes llamarlo al iniciar la app.

SyncWorker es un CoroutineWorker con las anotaciones HiltWorker y AssistedInject, necesarias porque WorkManager aporta el contexto y los parámetros en tiempo de ejecución. Si falla, devuelve retry hasta tres intentos y luego failure. Recuerda que esto exige la configuración de WorkManager en la clase Application que vimos antes.

Módulo 12. Formularios: voz, selectores y modo lote

Crear y editar una tarea comparten el mismo TaskFormViewModel y el mismo estado. La diferencia es que editar llama a loadTask con un id. El estado es una data class con título, notas, fecha, hora, categoría y regla de repetición, y cada campo se actualiza con update y copy.

Hay un modo lote: tras guardar, el formulario se reinicia pero conserva categoría y fecha, ideal para añadir muchas tareas seguidas. La entrada por voz usa el reconocedor del sistema mediante un Intent con RecognizerIntent y añade el texto al título. No necesita el permiso de micrófono, porque el reconocimiento lo hace otra app; ese permiso declarado sobra.

Las fechas y horas usan los diálogos clásicos DatePickerDialog y TimePickerDialog. La categoría usa ExposedDropdownMenuBox, y la repetición un menú con reglas diarias, semanales, mensuales y anuales. Aviso: la regla de repetición y el flag de hora solo viven localmente; Google Tasks no los recibe.

Al editar hay confirmación de borrado con un AlertDialog, y compartir la tarea usa un Intent ACTION_SEND envuelto en createChooser. Los mensajes de error o confirmación se muestran con un SnackbarHost.

Módulo 13. Pruebas con repositorios falsos

Gracias a la inversión de dependencias, los casos de uso se prueban en la JVM, sin emulador. En lugar de mocks, el proyecto usa un FakeTaskRepository respaldado por un MutableStateFlow. Es el equivalente a un fake en pytest: una implementación real pero en memoria. Las pruebas usan JUnit y runBlocking; en proyectos nuevos es mejor runTest de kotlinx-coroutines-test, que salta los retrasos virtuales.

Las pruebas existentes cubren el recorte del título, la excepción con título vacío, el agrupamiento de tareas por fecha y la creación de categorías. Para Flow, recoge el primer valor con first. Para ViewModels, usa un dispatcher de prueba para Main. Las pruebas de Room y de interfaz van en androidTest, con instrumentación.

Módulo 14. Proyecto integrador: hoja de ruta

Para reconstruir la app, avanza por hitos que siempre dejan algo ejecutable. Primero el esqueleto con Hilt. Después el dominio y las pruebas, sin Android. Luego Room y una lista que lea de la base de datos con datos sembrados. Con eso ya tienes una app local completa. La red y la sincronización van al final, porque son lo más difícil de depurar.

Módulo 15. Publicación en Google Play

Antes de publicar debes endurecer la compilación de release. Activa minificación y reducción de recursos con R8 y revisa las reglas de conservación, sobre todo para Gson, que usa reflexión sobre los DTO. Sustituye los identificadores de prueba de AdMob por los reales, tanto el de aplicación en el manifiesto como el del banner. Quita permisos innecesarios como RECORD_AUDIO.

Genera un keystore de subida y guárdalo fuera del repositorio; las contraseñas van en un archivo local o en variables de entorno, nunca en el control de versiones. Activa Play App Signing para que Google custodie la clave final. Compila un Android App Bundle, con bundleRelease, que es el formato requerido.

La huella SHA-1 de la clave que Google usa para firmar es distinta de la tuya: añade también esa huella al cliente OAuth. Publica la pantalla de consentimiento y, como el alcance de tasks es sensible, prepárate para la verificación de Google. En Play Console completa la ficha, la política de privacidad, la sección de seguridad de datos, la clasificación de contenido y la declaración de anuncios. Empieza con una prueba interna y luego cerrada antes de producción.
